# The mid-press drop and the release-build reboot rate (issue #38)

**Scope:** §12.2 validation row 7 / G-5 (is a pass resumed mid-press after a console-link drop a
problem?) and row 8 / G-7's second half (the 8/19 reboot rate is a DEBUG-build figure — what does
a release build at `INFO` measure?).
**Date:** 2026-10-03.
**Hardware on test host:** ESP32-S3-N16R8 on the CH9102 bridge, serial `5C930639851`
(`/dev/cu.usbmodem5C930639851`), paired to a real console for this session (the board's bond was
erased and re-established, §5).
**Image:** the shipped release build at `HEAD` (`c0a3933`): `CONFIG_MCU_DEBUG` off,
`CONFIG_LOG_MAXIMUM_LEVEL=3` (**INFO**), `CONFIG_CONTROL_UART_BAUD=115200`,
`CONFIG_FREERTOS_HZ=100`, on the committed `sdkconfig.defaults` + `sdkconfig.defaults.esp32s3`.
App `.bin` **547,056 B**, SHA-256 `191de3edf04ff87f96991554f04e9ccfcdba3c52274f4c77ff1d69d3b157b1be`.

Raw evidence is at `/tmp/ns38/evidence.json` on the bench host (ephemeral, not committed — the
durable numbers are below). The instrument is `scripts/bench_link_drop.py`; its pure parts are
pinned by `scripts/test_bench_link_drop.py` (13 tests, stdlib only).

---

## 1. The two results the ticket asked for

| # | Question | Measurement |
| --- | --- | --- |
| **G-5 / validation 7** | Is a pass resumed mid-press after a console-link drop a problem? | **No, and the condition was real.** A macro holding A for 60 s of every 60 s loop was dropped 42 s in, on the press record. The container sent **exactly one `STOP`**; the device read `IDLE` with a plain `CONTAINER_STOP` on the wire; the run's last notified state was the **press** (`020000000880000880`) and the stop's neutral was the last write; on reconnect the pass **did not resume** and no second `START` went out. The console never saw the resumed press. |
| **G-7 / validation 8** | The release-build reboot rate | **0 reboots in 21 disconnects**, 0 `Tmr Svc` stack overflows, 0 `rst:0xc`, across 20 sleep/wake cycles at `INFO` on the release build. The 8/19 belongs to the pre-fix console path on the base firmware, not to this build (§4). |

All 21 disconnects are `reason=531` (HCI `0x13`, the console ending it), as §9.1 records. Every
one of the 21 reconnections ran at `conn_itvl=4` (**5 ms**).

## 2. How the runs were produced

**Condition.** The release build, flashed from a clean incremental `idf.py build` of `c0a3933`
and pinned by the SHA above. No debug knob was changed: the release `INFO` condition is what the
ticket asked for, and it is also what the tree ships.

```sh
source ~/esp/idf-env-5.5.5.sh
idf.py build && idf.py -p /dev/cu.usbmodem5C930639851 flash     # container stopped (§10.2)
container/.venv/bin/python scripts/bench_link_drop.py --cycles 20 --out /tmp/ns38/evidence.json
```

**The instrument** drives the real `Controller` — the same `snapshot()` and log ring the four
screens render — and reads the device's own report-cadence meter (§7.5) out of the shared wire,
where the container's log demux already surfaces `ESP_LOG` text as `{source="device"}` lines. So
the device-side facts and the container-side facts come from one stream.

**Human actions.** Three, printed by the script as it reached each: wake the console for the run;
sleep it mid-press; wake it for the reconnect. The 20 cycles then ran **without per-cycle human
action** — a sleeping console keeps scanning for its bonded controller, the board wake-advertises
3 s after every drop, and the resumed reports wake it to the lock screen, where it sleeps again
(§9.1, and the loop §3.4 of `console-lifecycle-bench.md` describes). One cycle measured 16 s.

**The mid-press fixture** is generated by the script and compiles to two records:
`A` held at `t=0`, released at `t=60000` → frame 0 `020000000880000880` hold 60000, frame 1 the
neutral hold 0, `loop_ms = 60000`. So *any* drop during the run is a mid-press drop and the
condition does not depend on human timing. The script asserts frame 0 is a button press before
starting, and the plan identity on the wire was `6e651cab1cf5e6615deb80b3afde3dda`.

## 3. Half A: the mid-press drop

Timeline, from the instrument's evidence rows and the log ring:

| t | Fact |
| --- | --- |
| `00:48:33` | attached; console `CONNECTED`; `mid_press.json` committed and started; `mode=MACRO`, `currentFrame=0`, `plan_hash=6e651cab…` |
| `00:48:34` | the console **re-subscribed** mid-run — §4.6's RESUME path ran (rearm commits the neutral, then re-applies the current frame). The resume mechanism is reachable, which is why the stop matters |
| `00:49:15` | the console slept: `reason=531`. The drop landed with `mode=MACRO` and `currentFrame=0` — the press was on the wire |
| `00:49:15` | container: **one** `STOP`, `mode=IDLE`, `stopReason=CONSOLE_LOST`, no error, plan retained; device `last_stop_reason=CONTAINER_STOP` |
| `00:49:23–24` | the console reconnected (~8–9 s); after 5 s of settling: `mode=IDLE`, `startCalls=1`, `stopReason=CONSOLE_LOST` — no auto-restart, the drop story survives |

**The meter, verbatim** (the run's one readout at the stop):

```text
macro meter: applied=5 changes=5 inputs=2 notified=4168 dropped=0 failed=0 ring=2/64
macro meter: #0 d=0us g=3 n=1 s=000000000880000880
macro meter: #1 d=3274us g=4 s=020000000880000880
```

The two distinct notified inputs are the neutral (`gen=3`) and the **press** (`gen=4`,
`020000000880000880` = A in buttons byte 0). `notified=4168` over the 42 s run is 99.2/s on the
10 ms grid — validation 3's report period, restated on the release build. `applied`/`changes`
reach 5: arm-neutral, press, the re-subscribe's rearm-neutral, press, and the **stop's neutral**,
which is the run's last write and is notified on the next report period. That is the device-side
half of "left neutral rather than holding a press across the drop"; its last-write property is
pinned offline by `test/host/test_control_executor.c:493`
(`test_stop_commits_the_neutral` — a mid-record stop leaves the neutral last), so this run is the
condition and the console's tolerance, not a re-proof of §4.6.

**What the console saw.** After the reconnect it re-subscribed and the device — `IDLE`, its report
buffer holding the neutral — sent the neutral rather than a press. The instrument asserts the
container-side truth (no resume, no second `START`); a resumed pass would have required a
`MODE_CHANGED` back to `MACRO` and a `START`, and neither occurred.

**The unwatched case, for the record.** The stop is a *container* policy: it fires because the
container saw the drop edge and re-read `STATUS`. A drop that happens while the container's
control link is down (or before the container is attached) is §4.7's device rule — the pass keeps
running and resumes at its current frame on re-subscribe — and the container has no edge to act
on when it returns. That is not a defect in the policy; it is what ADR-0008 decides, and §9.3's
risk statement is about the watched case this half measured.

## 4. Half B: the release-build reboot rate

| Quantity | Value |
| --- | --- |
| Sleep/wake cycles | **20** (21 disconnects including A's drop) |
| `Tmr Svc` stack overflows | **0** |
| `rst:0xc` | **0** |
| `boot_id` changes during the cycles (`recovery: the device reported a boot`) | **0** |
| **Reboot rate** | **0 / 21** |
| Drop → reconnect | min **3 s**, median **4 s**, max **11 s**, mean 4.6 s (n=20) |

The only `boot_id` change in the whole session is the reset the port-open itself pulses when the
instrument attaches, before the first drop — the same reset every bench session starts from.

**Why the DEBUG figure does not carry over, in two steps.** §7.6 and
`advertise-restart-bench.md` already showed that the pre-fix callback is *latent* at `HEAD`: it
bottoms the 2048-byte timer task at **52 B** and did not tip in 41 disconnects at either baud,
while **8 overflows / 8 `rst:0xc` in 26** reproduced only on the base firmware, whose `ESP_LOG`
went straight to a driverless ROM console — a deeper log path than `HEAD`'s hook. The fix then
moved `ble_advertise()` off the timer task entirely. So at `HEAD` the observed rate is zero from
two independent directions: the work no longer runs on the short stack, and even if it did, the
path that overflowed is not `HEAD`'s log path. **A release build relaxes the log budget further
still** — but that is not what this number proves, and the record should not claim it: with the
fix in, a DEBUG build would also read zero here.

One consequence worth recording rather than assuming: the `restart_adv` task's minimum-ever free
stack is logged at `DEBUG` (§7.6), so the release/`INFO` build **silences the margin line**. The
release bench's evidence is the absence of reboots; the 2172 B margin remains #27's DEBUG
measurement.

**Two tolerated defects, seen unchanged.** All 21 connections logged
`ble_gap_update_params rc=3` / `failed to update connection parameters` (G-11's inverted
`itvl_min`/`itvl_max`, harmless and deliberately not fixed, §7.6 defect 2) and all 21 ran at
5 ms regardless. A 34 B plan staged cleanly (`staging closed: total=34B … drops=0`).

## 5. The pairing trap, reached again — and why `PAIR_UNPAIR` alone is not the fix

The first run of the session died at "wake the console": the board sat `ADVERTISING` with
`bond=PAIRED` for 240 s and the console never connected. That is #27 §4's stale-bond trap —
a bonded board wake-advertises (`g_adv_opcode = 0x81`) to the console it remembers, and a console
sitting on the grip-order screen ignores it.

The container exposes `PAIR_UNPAIR` (ADR-0013), so it is the natural first move. It clears the
bond (`bond=PAIRED` → `UNPAIRED`, measured) **and is not sufficient**: `ble_advertise()`
early-returns while `ble_gap_adv_active()` (`main/src/device.c:185`), so the board keeps
broadcasting the stale `0x81` advert and the console still does not list it. What works is the
#27 recipe, because it ends in a reboot:

```sh
python -m esptool --chip esp32s3 -p /dev/cu.usbmodem5C930639851 erase_region 0x9000 0x6000
```

The board boots unpaired, advertises pairable, and paired from the grip-order screen on the first
attempt. This is a bench-path fact, not a firmware defect being reported; it is recorded in §10.3
so the next session does not spend a 240 s timeout finding it.

## 7. What this settles for #38

- **G-5 is answered, not merely sidestepped.** The mid-press resume condition was real — a run
  holding A was dropped on the wire, and the console's own re-subscribe ran the executor's RESUME
  path earlier in the same run — and the container's one `STOP` ended it before the console
  returned. The device was left neutral: the stop's neutral is the mode's last write (§4.6,
  offline-pinned) and the last notified state the console could have acted on was the press.
- **The release build's reboot rate is zero over 21 disconnects**, so §9.2's "expect a reboot
  anyway" is now cheaper to hold: it stays as policy — a reboot has causes this callback never had
  — but the advertised failure mode is no longer a live rate on the shipped build.
- **The policy's limit is now explicit**: it covers the *watched* case. A drop the container does
  not see is ADR-0008's device rule and resumes at the current frame; nothing in this bench
  contradicts §4.7, and the design accepts it.

## 8. Not attempted

- **A pre-fix release build.** The ticket's comparison is against the DEBUG 8/19 and #27's
  before/after; isolating the log level further would need a second image built from the pre-fix
  `gap.c` at `INFO`, and #27's 52 B margin plus the 8/26 reproduction already attribute the rate
  to the log path rather than the level (§4).
- **`CONFIG_FREERTOS_HZ` and the sub-period holds.** Validation 3's fork (§7.5) is untouched;
  every hold here is far wider than the 10 ms report period.
- **The unwatched-drop case as a measured condition** (§3). It needs the control link torn down
  while the console drops, which is a different instrument.
- **The amiibo half of the rotation policy.** `features.amiibo` is still false on this firmware
  (#25/#32), as `console-lifecycle-bench.md` §3.5 records.
